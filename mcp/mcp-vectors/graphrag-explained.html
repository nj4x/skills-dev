🧠 GraphRAG Explained

mcp-vectors vs. Original GraphRAG Project

What is GraphRAG?

GraphRAG is a technique for building knowledge graphs from text documents. Instead of just storing text chunks, it:
  • Extracts entities & relationships from text (e.g., "Alice works at Company B")
  • Builds a knowledge graph connecting these entities
  • Detects communities (clusters of related entities)
  • Generates summaries of each community
  • Uses the graph for smarter retrieval instead of just semantic search

The Two Implementations

📦 mcp-vectors

  • Lightweight, local-first GraphRAG
  • Built as an MCP (Model Context Protocol) server
  • Uses LM Studio (local LLM)
  • SQLite graph storage
  • Can run offline, no cloud dependencies
  • Designed for code analysis with AST parsing

🌐 Original GraphRAG

  • Enterprise-scale, production GraphRAG
  • Developed by Microsoft Research
  • Pluggable LLM backends (OpenAI, etc.)
  • Flexible storage backends (Azure, local file, etc.)
  • Designed for large-scale document indexing
  • Hierarchical community detection
✨ Main Philosophy Difference: mcp-vectors prioritizes simplicity and local execution. The original GraphRAG prioritizes scalability and extensibility.

Entity Extraction: How They Find Information

🔍 mcp-vectors Approach

Uses a hybrid LLM + code analysis (AST) strategy:

Read chunk → Parse Python AST → Send to LLM → Extract entities → Iterative gleaning

Key feature: If indexing Python code, it first parses the AST to find functions, classes, and imports. Then the LLM adds semantic meaning to what it sees. This makes extraction more accurate for code.

🔍 Original GraphRAG Approach

Uses pure LLM extraction:

Read chunk → Send to LLM → Parse response → Iterative gleaning

Key feature: No structural parsing—relies entirely on the LLM to understand the text and extract entities. Works for any document type (articles, emails, code comments, etc.).

mcp-vectors Pros

  • More accurate for code (AST provides structure)
  • Finds functions, classes automatically
  • Reduces LLM hallucination in code

Original GraphRAG Pros

  • Works for any document type
  • Simpler, fewer dependencies
  • No need to parse file format
Both use identical "gleaning": After initial extraction, they ask the LLM: "Did you miss anything?" If it says "yes," they ask again. This iterative process finds entities missed on first pass.

Community Detection: Grouping Related Entities

After extracting entities and relationships, both systems group related entities into communities. Think of it as finding clusters: "These 5 people and 3 companies form a business unit."

🔗 mcp-vectors Algorithm

Try graspologic library → If fails, use NetworkX → If fails, create singleton clusters

Key feature: Graceful fallback. Even if the fancy algorithm isn't available, it still produces communities (one entity per community as worst case).

🔗 Original GraphRAG Algorithm

Use graspologic hierarchical Leiden (required)

Key feature: Uses hierarchical clustering, so you get communities at multiple levels (communities within communities within communities). This is powerful but requires the graspologic library to be installed.

mcp-vectors

  • Single-level communities
  • Fallback algorithms if needed
  • Lightweight, fewer dependencies
  • Handles empty graphs gracefully

Original GraphRAG

  • Hierarchical communities (multi-level)
  • More detailed structure
  • Requires graspologic library
  • Better for large, complex graphs
💡 Why hierarchical matters: If you have 1000 entities, hierarchical clustering gives you level-0 (all 1000), level-1 (100 macro-communities), level-2 (10 meta-communities). This lets you summarize at different zoom levels.

Report Generation: Summarizing Communities

After detecting communities, both systems generate summaries of what each community is about.

📝 mcp-vectors Approach

Separate facts from prose:

  • Facts (from graph): Entity names, file paths, relationship count (deterministic, always correct)
  • Prose (from LLM): Title, summary, key findings (LLM-generated, may be incomplete if LLM fails)

If the LLM fails or returns bad data, the facts are still correct. The prose just stays empty.

📝 Original GraphRAG Approach

Hierarchical context:

  • Uses child community summaries to build parent summaries
  • Tracks token budgets to fit summaries in LLM context window
  • Reports include rank, attributes, period, size
  • Generates reports for each hierarchy level

More complex but gives hierarchical summaries: overview → detail → detail.

mcp-vectors

  • Simple, flat report
  • Graph facts separate from LLM prose
  • Graceful degradation if LLM fails
  • Fast to generate

Original GraphRAG

  • Hierarchical reports
  • Context-aware (uses child summaries)
  • Token-budget aware
  • Richer metadata (rank, period, etc.)
mcp-vectors bonus: Handles LLM response format flexibly. If the LLM returns arrays instead of strings (like llama-3.2-1b-instruct does), it converts them automatically.

Storage & Caching: Where Does the Data Live?

💾 mcp-vectors

Three layers:

  • SQLite graph: Entities, relationships, communities stored locally in `~/.mcp-vectors/graphs/`
  • Qdrant vectors: Community summaries (embeddings) for fast similarity search
  • In-memory cache: LLM extraction results cached during a session (not persisted)

Everything stays on your machine. SQLite uses WAL (Write-Ahead Logging) for concurrent access.

💾 Original GraphRAG

Pluggable storage:

  • FileStorage: Writes to local JSON/Parquet files
  • Azure CosmosDB: Cloud-based NoSQL for enterprise scale
  • Azure Blob Storage: For large document archives
  • Abstract Cache: LLM response caching via pluggable backend

You choose where data goes. Designed for cloud-scale deployments.

mcp-vectors

  • Fixed: SQLite + Qdrant
  • Local-first (privacy)
  • No network calls
  • Session-based caching
  • Fast startup

Original GraphRAG

  • Flexible backends
  • Cloud-scale ready
  • Multi-region support
  • Persistent caching
  • More configuration
🔒 Privacy: mcp-vectors stores everything locally. Original GraphRAG can use cloud storage, which is powerful but requires security consideration.

Async & Background Tasks: How They Process in Real-Time

⚡ mcp-vectors

Task deduplication:

  • When files change, it schedules a graph rebuild
  • If a rebuild is already running, it doesn't spawn a second one
  • If files change during rebuild, it reschedules one more pass
  • This prevents thundering herd and redundant work

Graceful shutdown: When stopping, it waits for active operations to finish (up to 60 seconds by default).

⚡ Original GraphRAG

Workflow-driven batching:

  • Processes files in batches through a pipeline
  • Each stage is async-configurable: EAGER, SEMAPHORE, or THREADED
  • Progress callbacks notify you of advancement
  • Designed for "run once, index everything" rather than continuous updates

mcp-vectors

  • Continuous updates (watch mode)
  • Single-flight semantics
  • Backpressure handling (reschedule)
  • Real-time index updates

Original GraphRAG

  • Batch processing
  • Progress tracking
  • Flexible concurrency
  • Pipeline orchestration
mcp-vectors use case: Great for watching a codebase and keeping the index fresh as you edit files.

Original GraphRAG use case: Great for one-time indexing of a document archive.

Quick Comparison Table

Aspect mcp-vectors Original GraphRAG
Extraction LLM + AST parsing (code-aware) Pure LLM
Communities Flat (single-level) Hierarchical (multi-level)
Fallback Yes (graceful degradation) No (requires dependencies)
Report Generation Separate facts/prose Hierarchical context
Graph Storage SQLite (local) Pluggable (local/cloud)
LLM Cache In-memory (session) Pluggable backend (persistent)
Processing Model Continuous updates (watch mode) Batch processing
Best For Local code analysis, real-time indexing Enterprise indexing, document archives

🎯 When to Use Each

Use mcp-vectors if...

  • You want to analyze code (Python, etc.)
  • You need privacy (local-only)
  • You want real-time index updates
  • You have a small-medium codebase
  • You want to run offline

Use Original GraphRAG if...

  • You're indexing documents (articles, PDFs, etc.)
  • You need cloud scalability
  • You want hierarchical summaries
  • You have large enterprise archives
  • You need pluggable storage backends
💡 Fun fact: Both systems use the same delimiter scheme for parsing LLM output! `<|>` for tuples, `##` for records. This makes them compatible in spirit, even if implementation differs.
