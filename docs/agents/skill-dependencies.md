# Cross-skill dependencies

When changing a multi-turn skill, preserve its dependency contracts rather than treating each `SKILL.md` as isolated. The deduplicated dependency graph:

- `planning/critic` → `planning/repeat`: critic loads `repeat/SKILL.md` for the loop contract; falls back to an inlined contract if absent.
- `planning/repeat` → `session/mark`: with no args, `repeat` reads the mark file written by `/mark` to synthesise a task.
- `email/inbox` → `email/mail`: inbox delegates all IMAP access to `mail.py`; its final step can also invoke `publishing/html-view` if installed.
- `learning/grilling` → `planning/critic`: grilling automatically invokes critic at the end to audit ADRs; requires critic to be installed.
- `engineering/grill-with-docs` → `learning/grilling` + `engineering/domain-modeling`: delegates grilling to the grilling skill and doc creation to `/domain-modeling`. Inherits the grilling → critic dependency.
- `engineering/improve-codebase-architecture` → `learning/grilling`: invokes the grilling skill in its deepening loop.
- `engineering/setup-skills` → `dev/writing-for-agents`: when syncing an existing `docs/agents/*.md` file with its seed template, composes the merged text via `Skill("writing-for-agents")`; falls back to a section-by-section merge if absent.
- `engineering/refactor-tests` → `engineering/codebase-design` + `engineering/tdd`: Step 7b reads `codebase-design` for module, interface, seam, adapter, and quotes the seam definition from `engineering/tdd/SKILL.md` (the sentence starting "A **seam** is the public boundary you test at" under "Seams — where tests go") word for word. Keep the quote and those terms in step when either skill changes. The `seam` term in the quote means the external seam only (`codebase-design` internal seams are not test surfaces); keep the quote's added sentence identical to the one in that tdd paragraph. `reference/patterns.md` (Test doubles) also cites `tdd/mocking.md` for a patched port: the bold label `**1. Inject first**` under `## Placing a Double`. Keep that label and its guidance in step.
- `engineering/refactor-tests` → `engineering/to-tickets`: Step 11 stages drafts in the `to-tickets` spec-linked template and publishes them with `Skill("to-tickets")`. It also relies on the `to-tickets` slug rule, the manifest rewrite to `<tracker-ID> <NN>-<slug>` after a real-tracker publish, the promoted `issues/` directory on the local tracker, the per-ticket `label:` field, and the caller-declared headless mode in `to-tickets` Headless detection (ADR-0079). The dependency is optional at runtime: with no `docs/agents/issue-tracker.md`, Step 11 writes only the queue file. Change `render_review_queue.py` when any of those `to-tickets` shapes changes.
- `engineering/refactor-tests` → `docs/agents/testing.md` (seeded by `engineering/setup-skills`): reads two headings. "Test layout": the `Integration directory:` and `Guard:` lines (`SKILL.md` Step 2 "Cross-cutting classification", `reference/patterns.md` "Directory guard check"); an `Integration directory:` value overrides the table default only for the language it names, and a bare value belongs to the primary test language, defined once in `reference/patterns.md` "Language detection". "Assertion idiom": the `Raisers:` names passed as `--raiser` (Step 8 Evidence-free criteria). Reads no other heading. With no file, or a heading or key that reads `not set` (`Raisers: not set` included), falls back to the table defaults and the project-doc search and the names the project documents elsewhere. Keep the heading names and the `Integration directory:`, `Guard:` and `Raisers:` line keys in step with `skills/engineering/setup-skills/testing.md`.
- `engineering/testing` → `engineering/refactor-tests`: when ripgrep and `search-codebase` find no covering test, `testing` computes the expected test path with the `refactor-tests` mirroring convention. Changing the path templates in `skills/engineering/refactor-tests/reference/patterns.md` breaks `testing` silently; update `testing` in the same change.
- `engineering/setup-skills` → `engineering/refactor-tests`: Step 1 exploration reads `reference/patterns.md` "Language detection" (it defines the primary test language), "Runner detection (convention markers)" and "Path templates". Section E reads "Path templates" (path default), "Integration directory targets (cross-cutting tests)" (integration-directory default) and "Assertion vocabulary (dead-test detection)" (assertion prefixes). `setup-skills` copies none of it. Without `refactor-tests` installed, the values are `not set`. Renaming those five `patterns.md` headings breaks the seeding.
- `dev/code-review` → `engineering/tdd`: `skills/dev/code-review/docs/testing-standards.md` mirrors tdd `## Test shape`, `## Seams — where tests go` (check 2) and `mocking.md` (check 3, including its command definition: a call that crosses a boundary or port and is the observable outcome). Mirror an edit to one in the other. `code-review` reads the "Assertion idiom" line keys `Prefix:`, `Raisers:` and `Fixtures that assert:` (check 6, Severity); `tdd` Test shape items 4 and 5 state the same three. Keep the key names in step with the `setup-skills` template.
- `engineering/testing` → `docs/agents/testing.md` "Commands": the run commands and the covering-tests mapper come from that heading. The full-suite and one-file lines each fall back on their own, to the repo's AGENTS.md and then its runner config, when the file, the heading, or that line is missing or reads `not set`. The mapper line falls back, on the same conditions, to the script the repo's AGENTS.md or testing doc names; with none, `testing` uses its own mapping. `testing` reads no other heading, and runs no shuffle and prints no duration line, so "Order independence" and "Cost budget" have `tdd` and `code-review` as their readers, never `testing` (decisions #153, #156). Renaming "Commands" in the `setup-skills` seed template breaks `testing` silently; update `testing` in the same change.
- `engineering/to-spec` → `engineering/setup-skills`: requires `docs/agents/issue-tracker.md` written by `setup-skills`; prompts the user to run `/setup-skills` if absent.
- `engineering/to-tickets` → `engineering/setup-skills`: same dependency as `to-spec`. When the source is an existing issue, Step 7's real-tracker pass 3 also reads the **Make an issue a sub-issue of a parent** operation, and for its idempotency check the **List the sub-issues of a parent** operation, from that doc (the GitHub seed doc has both). With no such operation (GitLab and other seed docs), or when it fails at runtime, the ticket gets `Part of #<parent>` at the top of its body instead (ADR-0078).
- `engineering/to-tickets` → `engineering/implement`: Step 5 guidance recommends `/implement` for working the ticket frontier one slice at a time.
- `engineering/implement` → `engineering/testing` + `dev/code-review` + `publishing/pr`: runs covering tests via `Skill("testing")`, reviews through a fresh agent that calls `Skill("code-review")` with the brief from `render_review_brief.py`, and writes the PR body with `Skill("pr")`. It passes `pr` one issue-link line per GitHub-issue ticket (`Closes #<n>` or `Refs #<n>`, per the **Closing work** rule in the tracker doc), which the `pr` template's optional final block keeps word for word (the `### Issue links` rule in `pr/SKILL.md`); renaming that block or dropping the verbatim rule breaks ticket auto-close.
- `engineering/implement-spec` → `engineering/to-spec` + `engineering/to-tickets`: requires a published spec and a published task graph before it can run. Local tracker: `.scratch/<feature-slug>/spec.md` and `.scratch/<feature-slug>/issues/*.md`. Real tracker (GitHub, per `docs/agents/issue-tracker.md`): a spec issue and ticket issues linked by native blocking edges. Run `/to-spec` then `/to-tickets` first if either artifact is missing.
- `engineering/implement-spec` → `engineering/implement`: each implementer subagent runs `Skill("implement")` for its ticket, with a commit-only override (no push, no PR).
- `engineering/implement-spec` → `engineering/testing`: the integration Test gate runs `Skill("testing")` on the integration tip before round 1, and the integration fixer re-runs it after each fix.
- `engineering/implement-spec` → `dev/code-review`: the integration reviewer is a fresh `general-purpose` agent that calls `Skill("code-review")` with the brief from `render_review_brief.py`.
- `dev/code-review` → repo standards files: workflow Step 0.5 discovers the target repo's `CODING_STANDARDS.md`, `CONTRIBUTING.md`, coding sections of `AGENTS.md`/`CLAUDE.md`, and `docs/**/standards*` at every effort level, and passes the list to Finder C, the low-effort pass, and the mutating-mode roster and fixes; a repo document wins over the bundled Kotlin, Python, and testing standards. With none found, the bundled standards apply, with neighbouring tests supplying the testing facts. Step 0.5.1 also lists `docs/agents/testing.md` (seeded by `engineering/setup-skills`) as a whole-file entry; its headings are those of the `setup-skills` template. Review grades only the diff's tests: a testing-standard finding (from `testing-standards.md` or a language file's Testing section) on test lines the diff did not change (`in_diff: no`) is dropped, whether or not the file is touched, with at most one Note pointing the debt to `/refactor-tests`; security, correctness and other findings there still reach Pre-existing (rule: Step 0.5.4; also Synthesis, the `PRE_EXISTING` mapping and Step 4.9). Discovery runs inside code-review, so the `implement` review brief carries no standards list.
- `session/handoff`: optionally includes a "suggested skills" section to guide the fresh agent.
- `engineering/tdd` → `engineering/codebase-design`: `tdd/SKILL.md` "Seams — where tests go" says `codebase-design` also defines internal seams, which are not test surfaces. Keep that sentence in step with the `codebase-design` seam vocabulary.
- `engineering/tdd` → `docs/agents/testing.md` headings: `tdd` reads the file once at exploration and registers these fixed headings: "Test layout", "Seam declaration", "Stub helper", "Assertion idiom", "Parametrize idiom", "Order independence", "Cost budget". Without the file, `tdd` follows neighbouring tests, asks when unclear, suggests `/setup-skills` once, and never blocks. One general rule covers a heading or line key that reads `not set`: follow the neighbouring tests. "Seam declaration" keeps the language's public-export marker as its fallback; `Per-test call time:` reading `not set` means no budget check. A line with no key (`{language}: …`) that is absent means no fact. Keep the heading names in step with the `setup-skills` template.
- `engineering/implement` → `engineering/implement-spec`: the implementer's final result carries one line per seam the brief lists: `<seam>: <test id or path>`, or `<seam>: none — <reason>` (`<seam>: none — not declarable public: <why>` for a seam it cannot declare public). `implement-spec` writes one integration `--check` per `<seam>: <test>` pair. Keep the line format in step on both sides.
- `engineering/implement-spec` → `docs/agents/testing.md` "Seam declaration" heading: the per-seam `--check` asks whether each reported seam is declared public by that mechanism, with the public-export marker as the fallback when the file is absent or the heading reads `not set`. `implement` cites the same heading for its export rule. Keep the heading name in step with the `setup-skills` template.
